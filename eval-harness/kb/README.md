# Proposed knowledge-base changes

`product-guide.proposed.md` is the supplied guide with six insertions, generated by `build_proposed.py` (`python3 kb/build_proposed.py`). The evaluation itself still uses the unmodified `data/product-guide.md` as its only source of truth.

None of the insertions adds a new product fact:
- **Class (a)** restates something the guide already says, in a form and place retrieval will surface.
- **Class (b)** is a scope statement ("this guide does not document X"). It is true of the current guide, but the doc owner must confirm it is the intended policy.

## Does it help? (results section 9)

The check ranks guide chunks with keyword retrieval, close to Dify's Economical index, for each failing ticket.
- **Generation, not retrieval: TCK-1009 and TCK-1021.** The corrective fact already ranks first with the current guide, so a guide change will not fix these on its own. The guardrail has to.
- **Multi-part tickets: TCK-1006 and TCK-1015.** Querying the whole ticket pushes the fact out of the top 3. The proposed guide fixes TCK-1006; for TCK-1015 only querying the sub-question on its own fixes it. Split multi-part tickets before retrieval.
- **Gap: TCK-1005.** Nothing in the current guide mentions support levels. K5 gives retrieval something to find, so the assistant can route instead of inventing.

The probes are the failing tickets themselves, so this is a regression check, not evidence that the changes generalise. A vector (High Quality) index may rank differently.
